## 核实：L1 后续整理的职责分工

用户问 L4/L5/L6 是否由 worker 负责。核实结果：

- `RunSystem2Cycle`（operations/system2.go）五步：Consolidate（L1→L2，UPDATE 原地更新不建边）、Proceduralize（L1→L3，Retire 旧 playbook 建 supersedes 边）、L5（需 LLM+门控 CountRecentEpisodes≥MinEpisodesToRun，建 abstracts 边，每 N 周期合并）、L6（需 LLM+门控，水位线增量，TTL 过期 Retire）、Decay（总是跑）。
- worker 两个宿主：`ladym worker` CLI 进程（cli/worker.go）+ 引擎内嵌 `Engine.StartSystem2` goroutine（engine.go:430）。每周期跨进程 flock，锁被占则 standby 跳过，冗余副本不双跑。
- **例外：L4 没有自动维护**。写路径（Scope.RecordEvent→Episodic.Record）零建边；consolidate.go 无任何 PutEdge/Retire；全库 PutEdge 仅三个来源：显式 link()、supersedes Retire、L5 abstracts。ARCHITECTURE.md 声称的 "Auto-link on write" 未实现，文档超前于代码。
- 方案修正：operates_on 边应写时同步建（确定性、零 LLM，上游给了 resource_refs）；worker 负责槽位回填、别名合并、实体去重。分工 = write-time deterministic indexing + worker-time probabilistic grooming。

## L4 自动维护研究（结论：需要，四种机制）

代码证据——L4 三个问题（用户要求：用"问题/潜在问题"等直白术语，不用比喻性说法）：
1. **建边不足**：写路径/consolidate 零建边（已证）；code_refs 调用图存独立表从不投影进 edges，tier2Expand 只遍历 edges 表，ARCHITECTURE.md 声称的 "callers/callees via L4 expansion" 未实现（tier2 只有 symbol→file 的 metadata 回溯）。δ 中心性项（Graph 权重 0.15）形同虚设。
2. **悬挂边（dangling edge，指向已删记忆的边）+ 统计失真**：DeleteMemory 不级联删边（SQLite/Postgres 均只删 memories 行）；Decay 删 episode 留悬挂边；NeighborCounts 只查 valid_to IS NULL 不 join memories → 已删记忆通过悬挂边继续给邻居加中心性分，偏差随 Decay 累积；且每次 recall 都调 NeighborCounts。
3. **版本混淆**：schema 有 valid_from/valid_to 但除手动 Retire 外无人写；consolidate UPDATE 原地改 L2 fact 不建 supersedes 边，与 proceduralize/L5/L6 用 Retire 建边的行为不一致；code/indexer.go 无任何删除/清理逻辑。

外部证据：A-MEM 消融（去掉 link generation 性能降，去掉 memory evolution 时序题掉最多，temporal F1 39.4），但每条新记忆 k 次 LLM 调用未量化、无纠错；Zep/Graphiti 每写自动抽取+双时间轴失效（不删只关），成本高到 6 个月优化降 40%，remove_episode 有 episode 支持度级联规则；GAM 指出无边界的自动连边导致语义漂移（ladyM 的 layer/type 体系是天然桶边界）；A-TMA "ghost memory"：时间元数据存对了但检索混淆新旧状态。

判断：四种机制两档时机——写时确定性建边（operates_on、code_refs→edges 投影）+ 写时失效标注（consolidate UPDATE 复用 Retire 建 supersedes）+ worker 语义建链（A-MEM 式，门控，桶内连边）+ worker 垃圾回收（悬挂边清扫、NeighborCounts join memories）。优先级：GC（正确性）> 确定性建边（性价比）> 失效标注 > 语义建链。L4 自动维护与 L1 资源+动作方案互为前置。

## 第三次事实修正（FK 级联，impl-m0 实施中发现）

- edges 表 DDL 自带 `FOREIGN KEY(src_id/dst_id) REFERENCES memories(id) ON DELETE CASCADE`，SQLite 连接 `PRAGMA foreign_keys=ON`（store_sqlite.go:162），PG 同。新库公共 API 造不出悬挂边；我此前"DeleteMemory 不级联删边"结论只看了 DELETE 语句没看建表 DDL。
- 影响定级：P0-1/P0-2 从"现行 bug"降为"防御层"（无 FK 旧库/外部写库风险仍在，`CREATE TABLE IF NOT EXISTS` 不补 FK）。GC + EXISTS join 设计不变，仅测试造数绕 FK（事务外 PRAGMA 切换/PG DISABLE TRIGGER 后恢复），另加"FK 正常库 DeleteMemory 后 Neighbors 为空"回归锁。
- 教训三连：①BSD grep 不支持 `\|`；②Grep head_limit 截断；③**读 DDL 不只读语句**——级联行为在表定义里，不在 DELETE 语句文本里。
